# Final assessment and interview pack

Complete these with actual reports before reading the corresponding lesson solutions.

| Level | Assignment | Acceptance |
|---|---|---|
| Foundation | Explain a split, TF-IDF fit, a real citation, an HTTP error and an idempotency key | Correct units/types and one failure example for each |

Interview questions and answer criteria:

1. Can valid JSON be false? Yes; schema and factual support are separate checks.
2. Can a cited ID be real but irrelevant? Yes; evaluate entailment/relevance separately.
3. Can a retry duplicate a notification? Yes; a send can complete before local acknowledgment. Reconcile effects using stable IDs.
4. What makes this runner bounded? Fixed allowlist, argument limits, plan budget and stop-on-failure.
5. Why not let a retrieved passage choose a shell command? External data must not change application authority.
6. Is localhost health proof of deployment readiness? No; security, environment, scale and representative quality need their own checks.
7. What did transfer improve here? Nothing established: frozen-feature and raw-pixel target accuracies were equal in the observed split.
8. Why not declare the face dashboard fixed? Only its README/dependencies were audited; its stack and model/data permissions were not validated in a runnable environment.
9. What remains before a live Gemini success claim? Authorized key/model configuration and an actual measured request/evaluation.
10. How do you defend a capstone honestly? Show inputs, version, commands, expected/observed outputs, baselines, failure cases and limits. Distinguish mocks from live execution.

Worked support is in each new assignment's separate solutions and the release validation record. Do not invent model prices, latency, GPU speed or task-quality scores.
